# チャット基盤の共通化設計

## 今後の開発・取り込み方針

共通UIと接続処理の移行後、第二製品は派生リポジトリで実装し、このリポジトリの
改善をpull・mergeして取り込む運用を当面想定することにした。Errandは共通基盤の
利用製品として維持し、第二製品のために機能を削除しない。共通改善は取り込み元へ集める。
取り込み後は各製品で検証して配布する。具体的な開発ルールはルートの`AGENTS.md`を参照する。
以下の同一リポジトリ運用の記述は初期設計時点の想定であり、今後の運用はこの方針を優先する。

## 目的と今回の範囲

Errandの会話操作に対する改善を、アクセシビリティ試験・検証の伴走アプリなどにも
継続して反映できるようにする。同じ実装を参照し、コピーした派生版の同期を不要にする。
この文書は設計案であり、共通基盤や第二の製品はまだ実装していない。
新しい外部ライブラリの追加、公開、配布、既存設定の移行は今回の範囲に含めない。

当面は同一リポジトリ・同一コミットの共通コードを各製品が利用する。
開発中の変更は全製品で検証し、利用者への反映は各製品の配布更新時に行う。
基盤を独立パッケージに分ける場合のバージョン固定は、その段階で導入する。

## 現状から分かる境界

| 現在の実装 | 共通化する責務 | 分離する製品依存 |
| --- | --- | --- |
| `errand/ui.py` のConversation | 入力、発言表示、追従、移動、コピー、承認表示 | Sessionの直接生成、初期案内、ログイン・準備との結合 |
| 同Application・Window | 必要に応じて共通の画面枠・タブ制御 | アプリID、名称、メニュー、終了・非表示方針、設定・サービスの組み立て |
| `errand/session.py` | 会話状態、非同期イベント、中断、要求応答 | 小仕事向け指示、一時作業場所、ephemeral固定、Codex固有の送受信 |
| `errand/protocol.py` | app-server通信と子プロセス管理 | 実行ファイル探索、ランタイム探索、Errand向けエラー文 |
| Markdown・数式・elicitation関連 | 解析、描画、フォーム検証と回答 | 画面外の案件管理・判定は持ち込まない |
| settings・bookmarks・shortcuts | 検証、原子的保存、キー競合検出、部品 | 保存先、GSettings連携、製品固有アクション |
| runtime・login | Codex用の準備・ログイン処理 | 配置先、製品表示、採用するバージョン・配布方針 |
| extension・prefs・schemas・配布スクリプト | 将来必要になった部分だけ共通化 | GNOME連携と既存Errandの配布入口 |

Sessionには指示文の注入、AppServerにはコールバック、設定・定番依頼には保存先指定の
足場がある。ただしSessionの初期化・モデル取得・要約にも一時会話の前提があり、
引数を一か所追加するだけでは全経路の分離にならない。

## 目標構成と依存方向

基盤の仮のPythonパッケージ名を`chat_foundation`とする。名称は実装前に確定する。

```text
chat_foundation/
  core/              GTK非依存の会話データ・イベント・要求型
  gtk/               会話表示・入力・フォーム・共通操作
  codex/             app-server、セッション、ログイン、ランタイム
errand/              Errandの構成、指示、設定連携、起動入口
products/
  accessibility/     将来の専用アプリ（名称未定）
tests/
  ...                既存テストを維持し、責務ごとに順次整理
```

- `core`はGTK、Codex実装、各製品をimportしない。
- `gtk`は`core`の会話契約とGTK描画部品を利用し、製品やCodex実装をimportしない。
- `codex`は`core`の契約を実装する。GLib依存のdispatchは外から渡す。
- 各製品が画面とCodex接続・保存先・指示を組み立てる。基盤から製品をimportしない。
- GNOME拡張と既存`app.py`はErrandの入口として保つ。

最初からバックエンドの切替製品、プラグイン登録、動的ロードの仕組みは作らない。
Codexを最初の唯一の実装とし、画面との境界と疑似接続による検証に必要な契約だけ設ける。
Window全体の共通化は急がず、専用アプリが会話部品を別の画面枠へ配置できることを優先する。

## 製品から渡す情報と契約

次の名称は責務を示す仮称。実装時は既存イベントを調査して最小の型を確定する。

| 契約 | 含める内容 | 含めない内容 |
| --- | --- | --- |
| ProductDefinition | アプリID・名称・初期案内・製品のアクション | 任意のCodex設定を混在させた巨大な辞書 |
| ConversationPolicy | 指示、作業場所の所有・寿命、一時会話か、承認・権限の初期方針 | 案件データそのもの、認証情報 |
| ProductPaths | 設定・データ・キャッシュ・ランタイムの保存先 | 他製品の暗黙の保存先 |
| ConversationController | 送信、中断、要求への回答、終了、モデル選択、状態イベント | GTKウィジェットの操作 |
| 会話イベント | 発言ID・役割・本文更新、実行状態、構造化した確認要求、エラー | 生のJSON-RPCを画面全体へ公開すること |

要求にはID・世代を持たせ、二重回答と終了済み会話への回答を防ぐ。
受信はworker側、画面更新は注入したdispatch経由とする。タブ終了時は購読・タイマー・
要求・子プロセスを解放する。現在の世代管理、送信受付前の下書き保持を維持する。
会話本文のコピーは表示ウィジェットの走査から独立できるようにするが、
表のTSV変換と生成途中の最新本文を使う現在の挙動を変えない。

用途固有の画面は、会話部品を親画面に配置し、その隣に製品側のパネルを置く方式を第一候補とする。
会話内に専用表示が必要になった時点で、必要な追加契約だけ設計する。
製品名による条件分岐や、製品ごとのConversationサブクラスに共通処理のコピーを置かない。

## SKILL・MCP・案件状態の責任

基盤はCodexへの依頼とツール状態・確認の表示を担当する。
どのSKILLとMCPを使うか、導入方法、起動前の利用可否確認は専用製品が定義する。
現状は利用者のCodex設定を利用しており、専用構成の分離やツール制限は未実装。
指示文にツール名を書くことと、利用可能なツールを技術的に制限することを区別する。
専用構成の渡し方は、実装時に対象Codexの実際の仕様・対応状況を確認して決める。
既存Codex設定を自動編集したり、権限を暗黙に広げたりしない。

試験対象、適用基準、進捗、証跡、判定理由、人が確定した判定は専用製品の案件データとする。
共通チャットの本文やthread IDだけを正本にしない。会話の保存・スレッド再接続と、
案件の保存・再開は別の機能として設計する。保存を有効にするだけで再開できるとは扱わない。
第二製品の案件スキーマ、保存・復元、報告書生成は後続の製品設計で扱う。

## 互換性・データ分離

- ErrandのアプリID、CLI入口、GNOMEスキーマと起動、既存設定・定番依頼・
  ランタイムの保存先を維持する。パッケージ移動に伴う既存起動入口は薄い委譲で保つ。
- 第二製品には別のアプリIDと保存先を割り当てる。認証はCodex管理のままとし、
  設定・案件・承認の記憶をErrandと暗黙に共有しない。
- 一時会話・read-only・ネットワーク無許可の既定、承認の適用範囲、
  未対応フォームを続行させない挙動は維持する。基盤化を理由に権限を変更しない。
- CSSは共通部品用の名前へ段階的に移し、同一プロセス内の複数表示でも影響が混ざらないようにする。
- GTK/libadwaitaを使うデスクトップ基盤が対象。ウェブ画面の直接共有は対象外。

## 移行順序と各段階の完了条件

1. **Errandの製品構成を明示する。** 名称・案内・指示・保存先と会話方針を外から渡す。
   Sessionの通常送信・モデル取得・要約の各経路を確認し、既存値が既定のErrand構成で
   再現されることを完了条件とする。ファイル配置の大移動は同時にしない。
2. **独立した部品を移す。** Markdown・数式・フォームと通信を責務ごとに移す。
   通信から実行ファイル探索を分け、旧入口からの利用と配布物への収録を確認する。
3. **会話画面と制御を分ける。** Sessionの直接生成とログイン・準備の組み立てを製品側へ移す。
   基盤の会話画面が疑似Controllerだけで表示・操作でき、Errandで同じ操作が通ることを確認する。
4. **第二構成の最小検証を作る。** 仮の製品定義と保存先、隣接パネルを使う開発用構成で
   同じ会話部品を再利用する。実SKILL・MCPや完成した案件管理はこの確認には不要。
   製品を切り替えても名称・設定・状態が混ざらず、基盤修正をコピーせず反映できれば完了。
5. **専用製品を設計・実装する。** 案件保存、SKILL・MCP構成、判定と証跡の管理を追加する。
   この段階は共通基盤化とは別の作業単位とする。

各段階を独立したレビュー単位にし、Errandの改善を継続できる状態を保つ。
全面移動と機能追加を一つの変更にまとめない。製品間で要件が異なる場合は共通動作を
無理に統一せず、具体的な方針の差として製品側へ戻す。

## 検証と変更の運用

- 既存のsession・通信・終了・設定・描画・フォームのテストを継続する。
  既存テストは配置変更だけを理由に削除せず、意味のある挙動の確認を維持する。
- 共通契約の追加時に、疑似app-serverで送信・中断・承認・切断・遅延通知を確認する。
  第二構成では特に保存先の分離と終了処理を確認する。
- GTKの操作検証は既存の分離Wayland・別D-Bus・一時設定で行い、
  スクロール、発言移動、コピー、入力保持、キー設定、フォームを確認する。
- LinuxのGNOME ZIPとmacOSバンドル・対応ソースZIPの生成処理を確認し、
  共通パッケージの欠落を防ぐ。Mac固有の動作は実機未確認のまま明記する。
- 共通部品の不具合修正は基盤へ入れ、製品側に同じ修正を複製しない。
  基盤変更時は利用中の全製品の関連チェックを実施し、製品固有変更はその製品を検証する。
- 一つのコミットで検証したソースを各製品に収録する。配布時には使用コミットを追跡可能にする。
  独立パッケージ化は別リポジトリや異なる更新周期が実際に必要になった段階で検討する。

## 今回の記録と次の作業

行ったこと：現行の画面・Session・通信・保存・配布の結合を調べ、境界と移行順序を設計した。
理由：Errandの継続改善を他製品にも共有し、既存利用への影響を小さくするため。
未完了：基盤の実装、契約の具体的な型、第二製品の仕様、専用SKILL・MCPの構成検証。
次の作業：この設計をもとに段階1の変更範囲と検証を具体化し、実装の依頼後に着手する。
